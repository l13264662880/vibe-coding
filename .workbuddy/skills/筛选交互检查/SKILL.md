# 筛选交互检查

这个 Skill 只做一件事：验证待办页的筛选功能（状态 tab + 搜索框）在三种情况下是否都正确。

## 检查前

1. 用浏览器打开 `index.html`（推荐 Live Server：`http://localhost:5500`）。
2. 确认任务列表已经渲染出来（首次打开会有 mock 种子数据）。

## 三条检查（必须全部通过）

### 情况一 · 有结果

- 操作：点「进行中」tab，或在搜索框输入一个确实存在的关键词。
- 预期：列表只显示符合条件的任务；出现「共 N 条 · 匹配 M 条」，且 M ≥ 1。

### 情况二 · 无结果

- 操作：在搜索框输入一个不存在的关键词（例如 `zzzz`），或切到「已完成」而当前没有已完成任务。
- 预期：列表清空；显示「没有符合条件的任务。换个筛选，或清空搜索。」；计数为「匹配 0 条」。

### 情况三 · 清空恢复

- 操作：清空搜索框，把状态 tab 切回「全部」。
- 预期：列表恢复为全部任务；计数提示消失；「第一件事」高亮区恢复正常。

## 判定标准

- 三条全部符合预期 → 通过。
- 任何一条不符 → 不通过，指出是哪一条、实际看到了什么。

## 边界（只检查，不改代码）

- 状态 tab 与搜索词是叠加（AND）关系：先按状态筛，再按关键词筛。
- 已完成任务沉底、拖拽排序不受筛选影响——这些不在本 Skill 的检查范围内。

## 可访问性检查（余力加练）

除上面三条功能检查外，再核对筛选交互的可访问性：

| 检查项 | 要求 |
|---|---|
| 状态 tab 的角色 | `role="tablist"` + 每个按钮 `role="tab"` |
| tab 选中状态 | `aria-selected` 与当前激活 tab 一致 |
| 搜索框名称 | 有 `aria-label`，读屏能读出「搜索任务」 |
| 结果播报 | 筛选结果变化（计数 / 空提示）通过 `aria-live` 播报 |

可访问性缺陷不阻塞三条功能检查的通过判定，但应单独记录。
